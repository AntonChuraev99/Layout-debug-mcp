# layout-debug-mcp

Локальный инструмент: показывает работающий UI (Android-устройство через adb или страницу в браузере), даёт выделить конкретный слой layout прямо на картинке, **подвигать элементы с компьютера так, чтобы менялась картинка на самом устройстве**, и отправить правку в AI-агента — вместе с артефактами, по которым агент понимает, о каком элементе речь и где его править в коде.

## Проблема

Вёрстка идёт «по тексту»: описал словами → агент поправил → пересобрал → посмотрел → снова описал словами. Подвинуть кнопку на 8dp, поменять порядок элементов в карточке, поиграть отступами — цикл в десятки итераций, где половина времени уходит на объяснение, *какой именно* элемент имеется в виду.

Референс по ощущению — Layout Inspector в Android Studio, но нужна только одна его способность: **выделить слой**. Остальные инструменты не нужны, зато нужен чат с агентом и перетаскивание.

## Две цели

| Цель | Технология | Как снимаем |
|---|---|---|
| **Android** | Jetpack Compose / Compose Multiplatform | adb + debug-библиотека в приложении |
| **Web** | нативный веб (React + Tailwind), обычный DOM | dev-сервер + инжект в страницу |

Compose Multiplatform на wasmJs (canvas) — **не цель**. Веб здесь означает настоящий DOM.

## Главный сценарий

1. UI запущен: приложение на устройстве или страница на dev-сервере.
2. В окне инструмента — картинка. Кнопка **Screenshot**.
3. По нажатию: снимок + дерево layout.
4. Скриншот интерактивен: наведение подсвечивает элемент, клик выделяет. Выделяется любой уровень — вся карточка, строка внутри неё, отдельный текст. Хлебные крошки родителей для перехода вверх по дереву.
5. Пользователь пишет правку в чат: «эта кнопка должна быть шире и с отступом сверху».
6. К сообщению прикрепляются артефакты выделенного узла — агент понимает, о каком элементе речь, и правит код.
7. **Drag:** элемент перетаскивается мышью в окне на компьютере — **и уезжает на самом телефоне, сразу, без пересборки**. Наигрался → «Применить» → агент вписывает результат в код.

## Архитектура

Ядро — **нормализованный снапшот**. Оба адаптера отдают один и тот же формат, UI и мост к агенту не знают, откуда пришли данные.

```
        ┌──────────────────────────────────────┐
        │        Node backend (сессия)         │
        │  снапшот · выделение · очередь правок│
        └──┬──────────┬──────────┬─────────────┘
   adb     │          │ WS/HTTP  │ stdio MCP
  ┌────────▼───┐  ┌───▼──────┐  ┌▼───────────────────┐
  │ Android    │  │  Web UI  │  │ Claude Code сессия │
  │ adapter    │  │ (браузер)│  └────────────────────┘
  └────────────┘  └──────────┘
  ┌────────────┐
  │ Web adapter│  ← dev-сервер целевого проекта
  └────────────┘
```

**Backend** — единственный, кто трогает adb и dev-сервер. Держит сессию: снапшот, выделенный узел, очередь правок.

**Web UI** — страница в браузере, не Electron (не нужна упаковка, обновление и подпись). Скриншот + SVG-оверлей с боксами узлов + панель чата.

**Два входа для агента** поверх одного состояния:
- Чат в окне — свой агент в backend на `@anthropic-ai/claude-agent-sdk` (проверено 2026-07-26: актуален, бандлит нативный бинарь Claude Code, поддерживает MCP/subagents/hooks, Node 18+).
- MCP-сервер — когда пользователь работает в терминальной сессии Claude Code и хочет вытянуть «что сейчас выделено» оттуда.

MCP — это pull: агент забирает сам, инструмент его не разбудит. Поэтому чат в окне идёт через Agent SDK, а MCP остаётся вторым, ручным входом.

## Формат снапшота

```
Snapshot {
  id, target: "android" | "web",
  screenshot: png,
  density: { scale, unit: "dp" | "css-px" },
  root: Node
}

Node {
  id, parentId, children[],
  bounds: { x, y, w, h },        // в пикселях снимка
  boundsUnit: { x, y, w, h },    // в dp / css-px
  kind,                          // Column, Text, div, button
  label,                         // текст или contentDescription
  anchors: {                     // якоря для поиска в коде
    testTag?, resourceId?, className?, dataAttrs?
  },
  source?: { file, line }        // если адаптер смог
}
```

`source` — необязательное поле, но именно оно превращает инструмент из удобной указки в реальный ускоритель. Без него агент ищет по `anchors` грепом.

## Адаптер Android (сложная часть)

**`uiautomator dump` для Compose не годится как основа.** Он отдаёт accessibility-дерево: только semantics-узлы, плоско и обеднённо. `Column`, обёртки, контейнеры карточки в нём просто отсутствуют — а выделение произвольного слоя и есть главная фича. Годится как аварийный fallback, когда debug-библиотеку подключить нельзя.

**Основа — debug-only библиотека внутри приложения.** Подключается в debug-сборку, обходит настоящее дерево Compose и отдаёт узлы с границами и позицией в исходнике.

Механика (проверено 2026-07-26, требует спайка на реальном проекте):
- `androidx.compose.ui:ui-tooling` даёт `CompositionDataRecord` + composable-обёртку `Inspectable`. Ею оборачивается корень контента в debug-сборке — композиция начинает писать данные в store.
- `CompositionData.asTree()` из `androidx.compose.ui.tooling.data` разворачивает это в дерево `Group`: у каждого есть `box` (границы) и source-информация от компилятора — файл и строка. На этом же API работают Layout Inspector в Studio и библиотека Radiography.
- Ограничения принять сразу: API помечено `@UiToolingDataApi`, стабильность не гарантирована; source-информация пишется компилятором Compose только когда `sourceInformation` включён — в release он вырезается, но нам нужен только debug.

**Как дамп выходит наружу.** Крошечный HTTP-эндпоинт внутри debug-сборки + `adb forward tcp:PORT tcp:PORT`. Backend дёргает эндпоинт и получает JSON. Побочная выгода: тот же эндпоинт снимает и картинку (PixelCopy окна) — **скриншот и дерево становятся атомарными**, что невозможно при связке `screencap` + `uiautomator dump` двумя отдельными вызовами.

**px → dp.** Плотность отдаёт сама библиотека (`Density.density` из композиции), fallback — `adb shell wm density`.

## Адаптер Web (простая часть, но с прецедентами)

DOM отдаёт полное дерево с точными границами (`getBoundingClientRect`) без всякой магии. Захват — инжект скрипта в страницу через dev-сервер или CDP; скриншот — `Page.captureScreenshot` по CDP.

**Source mapping сломан у React 19** — `_debugSource` из fiber удалён (PR #28265), на нём держались LocatorJS, click-to-component, react-dev-inspector, code-inspector. Живой подход сейчас — **инжект на этапе компиляции**: babel/vite-плагин дописывает каждому JSX-элементу `data-source-loc="file:line"`. Это и надёжнее fiber-полей, и работает в Next.js/Vite/Webpack одинаково.

**Fallback без плагина — Tailwind.** Строка классов вроде `flex items-center gap-3 rounded-2xl px-4 py-3` почти всегда уникальна по репозиторию. Как якорь для грепа это сильнее, чем всё, что доступно на Android.

### Прецеденты: веб-половина во многом уже решена

Onlook, Frontman, Vibedit, LocatorJS, code-inspector — всё это про «кликнул элемент в браузере → правишь код / описал правку словами». Изобретать веб-часть с нуля незачем: подход к source mapping брать оттуда.

**Ценность этого проекта не в вебе, а в связке.** Compose-половина не решена никем за пределами Android Studio, а Studio не умеет отдавать выделенный узел агенту. Одно окно, один чат и один формат артефактов на обе платформы — вот чего нет ни у кого. Основной бюджет усилий — в Android-адаптер.

## Живое редактирование (ядро продукта)

Правка делается на компьютере, а меняется картинка **на телефоне** — сразу, без пересборки. Это не бонус к выделению слоёв, а то, ради чего инструмент существует: «поиграть кнопками» невозможно, если каждая попытка стоит полторы минуты gradle.

Цикл: **играешь вживую → применяешь → агент пишет код**. Оверрайды живут только в памяти работающего приложения; исходником они становятся отдельным осознанным шагом.

### Готовые механизмы не подходят

- **Compose Hot Reload** (JetBrains, 1.1.1 от мая 2026) работает на JetBrains Runtime и целится в desktop JVM. Для Android предлагается обходной путь — отдельный desktop-модуль. На устройство не работает.
- **Live Edit** в Android Studio делает ровно то, что нужно (свап DEX + инвалидация composable, API 30+, AGP 8.1+), но живёт внутри IDE. Публичного API или CLI нет — из нашего Node-backend не подёргать.
- **Пересборка** `./gradlew installDebug` — 30–90 секунд. Годится как замыкание цикла после «Применить», но не как игра.

Вывод: канал оверрайдов пишем свой, в той же debug-библиотеке.

### Канал оверрайдов

Библиотека держит `Map<nodeId, Override>` (offset, padding, size, visibility) как Compose-state. Backend шлёт правку по тому же `adb forward`-каналу, стейт меняется, композиция перерисовывается — телефон обновился за миллисекунды.

Вопрос в том, **куда воткнуть точку применения**. Два кандидата:

**Путь A — явный хук (надёжный, скучный).** Библиотека даёт `Modifier.tweakable("id")`, читающий оверрайды. Расставляется по элементам, с которыми работаем. Расставлять может сам агент: «хочу поиграть с этим экраном» → он один раз дописывает хуки, одна пересборка, дальше бесконечная живая игра. Никакой рефлексии во внутренности, ломаться нечему.

**Путь B — без правки кода (спайк).** До `AndroidComposeView.root` мы и так дотягиваемся рефлексией ради дерева. `LayoutNode.modifier` — изменяемое поле; подмена на `Modifier.offset(...).then(original)` инвалидирует measure и двигает элемент без единой правки в приложении. Риск: ближайшая рекомпозиция этого composable вернёт модификатор из кода и сотрёт оверрайд. Для игры с layout, когда больше ничего не меняется, скорее всего держится; проверить спайком, переприменять оверрайд после каждой композиции.

Путь A — основа. Путь B — если спайк подтвердит, становится режимом «zero-touch». Компилятор-плагин, автоматически вставляющий хук во все composable, **не берём**: цена и хрупкость на каждой версии Compose не окупаются.

### На вебе это бесплатно

DOM меняется вживую по определению: правим inline-стили — страница обновилась. Ровно так работают Onlook и Vibedit. Асимметрия сознательная: веб получает живое редактирование даром, Android требует канала оверрайдов.

### Что уходит агенту при «Применить»

Семантика перемещения неоднозначна: «подвинуть на 16dp вправо» — это padding, offset, изменение Arrangement или spacer? Решает агент. UI отдаёт сырьё: дельта в dp, границы до и после, границы родителя, соседи по родителю, накопленный список оверрайдов по узлу.

### Как видно, что телефон изменился

Тот же debug-эндпоинт отдаёт снимок и дерево за один вызов — можно дёргать несколько раз в секунду и получить «почти живой» вид, достаточный для вёрстки. Полноценный видеопоток через scrcpy остаётся на потом, для плавного взаимодействия.

## MCP-инструменты

| Инструмент | Отдаёт / делает |
|---|---|
| `capture` | новый снапшот, возвращает id |
| `layout_snapshot` | дерево последнего снапшота, сжатое (без шумовых узлов) |

## Этапы

**Два спайка — оба взяты** (2026-07-26, на реальном приложении: KMP, Compose Multiplatform 1.11, Kotlin 2.3.20, эмулятор API 36).

1. *Дерево — есть.* `asTree()` отдаёт боксы в px и `file:line` прямо в код проекта (например, `PremiumBanner.kt:87`). Путь A с явным `Modifier.tweakable` не понадобился.
2. *Оверрайд — есть.* Подмена `modifier` рефлексией двигает реальный элемент на устройстве без пересборки; сброс возвращает исходный модификатор.

Что выяснилось по ходу и стало частью решения:

- **Одной корневой `compositionData` мало.** `SubcomposeLayout` (Scaffold, ленивые списки, NavDisplay) композит контент в отдельную композицию со своей slot-таблицей. Читая только корень, теряешь почти весь экран. Нужен `LocalInspectionTables` с общим `MutableSet<CompositionData>` — рантайм сам докладывает туда каждую новую таблицу.
- **`ComposeUiNode` в CMP 1.11 `internal`.** Прямой каст не компилируется, аксессоры ищутся рефлексией по префиксу `getModifier`/`setModifier` (Kotlin манглит имена internal-членов).
- **Сырое дерево нечитаемо**: 495 узлов, глубина 67, один видимый элемент — цепочка `Scaffold → Surface → CompositionLocalProvider → Box → Layout → ReusableComposeNode` с одинаковыми боксами. Схлопывание цепочек с идентичным боксом на **внешний** узел (у него call-site в коде проекта, у внутренних — в Compose) даёт 155 узлов и глубину 5. Плюс наследование ближайшего LayoutNode вверх — иначе двигать можно только 85 узлов из 495, а выделяют обычно call-group.
- **Сдвиг применяется к выделенному узлу, а не к его содержимому.** Взяли внутренний `Row` — уехало содержимое, а фон и обрезка остались на месте. Для «подвинуть элемент» нужен внешний узел; UI должен показывать это через хлебные крошки.

**MVP — веб. Сделано** (2026-07-26). Инспектор в целевой странице, нормализованный снапшот, окно с iframe и оверлеем, выделение слоя, живой drag и resize через inline-стили, чат на Agent SDK, очередь правок, MCP-сервер с тремя инструментами, демо-страница для проверки без настройки. Подробности запуска — [README](./README.md).

**v1 — Android. Сделано** (2026-07-26). Агент в приложении (`LayoutDebugBridge` в commonAndroid + debug-source-set в androidApp), Node-адаптер поверх `adb forward`, второй режим окна: снимок устройства вместо iframe с тем же оверлеем, выделение, живой drag, сброс. MCP и чат не менялись — снапшот один на обе цели.

Что пришлось поправить в общем коде из-за Android:

- **Хит-тест был «самый глубокий узел»** — на Compose это неверно: ветки-соседи сидят на очень разной глубине, и полноэкранная обёртка оказывается глубже элемента под курсором. Правило заменено на «самый тесный бокс, глубина только разрешает ничью».
- **`styles` был CSS-формы** (`display`, `margin`, `padding`). В Compose таких понятий нет, а полезное — имя composable, источник, размер в dp — не имеет CSS-аналога. Стал плоским мешком `Record<string, string>`, каждый адаптер кладёт что есть.
- **Единицы разъехались.** Боксы должны совпадать со снимком 1:1, а агенту нужны dp. Введён `pxPerUnit`: боксы и оверрайды всегда в пикселях кадра, делишь — получаешь то, что пишется в код.
- **Устройство помнит правки, окно — нет.** После перезагрузки окна id, которыми они адресовались, потеряны. Первый снапшот сессии сбрасывает устройство в управляемое состояние (та же болячка была на вебе).

**v2.** Живой стрим через scrcpy: локальный Node пушит `scrcpy-server` по adb, мультиплексирует в WebSocket, браузер декодирует H264 через WebCodecs — паттерн ws-scrcpy-web (проверено 2026-07-26; WebCodecs только в Chromium). Сравнение снапшотов до/после.

## Стек

- Node 20+, TypeScript
- Backend: Node + `ws`; adb — прямые вызовы бинаря через `child_process` (прозрачнее обёрток вроде adbkit, ошибки adb видны как есть)
- Frontend: Vite + React, оверлей на SVG
- MCP: `@modelcontextprotocol/sdk`, stdio-транспорт
- Агент: `@anthropic-ai/claude-agent-sdk`
- Android debug-библиотека: Kotlin, `androidx.compose.ui:ui-tooling`, HTTP-эндпоинт только в debug

## Конвенции

- Инструмент **не правит код целевого приложения сам** — собирает контекст и отдаёт агенту.
- Ни один путь не падает молча: adb не найден, устройство не подключено, дамп пустой, debug-библиотека не подключена, dev-сервер не отвечает — каждый случай даёт видимое сообщение в UI с причиной и следующим шагом.
- Никакого кода инструмента в release-сборке целевого приложения. Android-библиотека — только `debugImplementation`, веб-плагин — только `apply: 'serve'`.
- Пути к устройству и к репозиторию — конфиг, не хардкод. Инструмент переносим между проектами.
